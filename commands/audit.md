---
description: Expert audit of existing code (security, performance, architecture or all): read-only experts report what is good and what is wrong in their area
---

Usage: `/swiftcraft:audit <security|performance|architecture|all> [path or feature]`. Without a path, audit the current changes (`git diff` plus untracked files); if there are none, audit the whole project.

1. **Scope and cost first.** Decide the scope, count its files, and tell the user which experts will run. `all` runs three reviews, so say that the cost is about three times a single audit, and wait for a go-ahead before starting it.
2. **Run the experts, read-only.** Use the agents `security-auditor`, `performance-auditor` and `architecture-auditor` (parallel for `all`, each in its own fresh context, none seeing the others' output). They only have Read, Glob and Grep: they never edit, and you must not edit either. Give each the scope and where the project rules are (`docs/constitution.md`, `docs/architecture.md`, `odd/tasks/`, `docs/adr/`). For the architecture expert, first run `node "${CLAUDE_PLUGIN_ROOT}/scripts/arch-graph.js" check` (JavaScript/TypeScript only) and pass its output as evidence to confirm. If the graph check cannot run (another language, an error), tell the expert "no graph output is available" so its report says so; the expert cannot run the tool and must never claim it did.
3. **Paste each expert's report verbatim.** Never rewrite, paraphrase or summarize it: show the complete report as the expert returned it, with its sections (Scope, Verdict, What is good, Findings, Not verified), the whole table and every finding with its `path:line`. Never print a secret an expert found; the location is enough. For `all`, put each report under its own heading, then, after the reports and clearly apart, a short table of your own (area, verdict, count of critical and high findings). Your own comments come after the reports, never in place of them. If a report contradicts itself or claims something the expert could not have done, say so in your own words after it.
4. **Do not fix anything.** Ask the user which findings to turn into work (`/swiftcraft:odd`). Save the report to `docs/audits/<date>-<area>.md` only if the user asks for it; the experts themselves never write files.

These reports come from reading code, not from running it: findings about performance are hypotheses to measure, and the "Not verified" section says what was not covered.
